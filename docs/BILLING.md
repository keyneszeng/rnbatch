# rnbatch 收费能力：额度与订单基础（研发分支）

> **当前版本不能直接在线收款。** 本功能是收费系统的安全基础，不是正式支付服务。请勿在网站上展示收款二维码或要求用户私下转账。公开收费前先完成产品、安全、商户、税务和退款政策验收。

## 设计决定

- 现阶段仍维持 **Web App 优先**；不改变原本 CLI/MCP 对本地文件的使用方式。
- 每位登录用户每月（**UTC 月份**）免费成功改名 **20 个文件**。预览、上传和下载不消耗额度。
- **按成功更名的文件数**计费，而不是按整个文件夹的文件数。成功执行后若用户撤销，也不退回已消耗额度（应在真实收费前收集用户反馈）。
- 额度分两层：每月免费额度（不结转）＋**会员订阅**（订阅生效期内不限改名次数）。
- 订阅价格：**月度 ¥9.9/月**、**年度 ¥99/年**。续费从原到期时间往后延，不吞掉剩余天数。
- 额度变更由服务器以 SQLite 事务实现；请求者不能在 HTTP 中指定订单金额、修改使用量、手动增加额度或声称支付成功。
- 明确标注：所有金额只是定价草案，实时线上付款不可用。

## 数据设计

在原有 `users.sqlite3` 数据库里添加：

- `billing_subscriptions`：按用户记录生效中的订阅套餐与到期时间（UTC 秒）。
- `billing_usage`：以 `workspace_id` 唯一键记录文件改名的预留额度、成功确认及 UTC 账期。会员用量记 0，不消耗免费额度。
- `billing_orders`：不可变的套餐价格快照、待处理与已核销状态、外部支付凭据唯一键；`days` 记录该订单兑现的订阅天数。

升级不会改写用户密码或现有登录表。运行新代码时自动创建这三个表。**部署前务必对 SQLite 数据库做安全备份。**

### 扣费过程

1. 用户登录并上传文件，提取关键词，生成预览 token。
2. 服务端在用户独立工作区锁内检查预览确认 token，再根据该预览的实际改名数量申请额度。
3. SQLite `BEGIN IMMEDIATE` 事务核验免费余额和预付余额并**原子预留**，避免同一账号并发超支。
4. 文件操作失败则自动释放预留、恢复已购额度；成功后把预留转成已结算记录。
5. 同一工作区不能重复扣费；已结算后的撤销不退额度，用户可以创建新工作区再次操作。

**故障边界：** 额度数据库和实际文件操作不是分布式事务。如果服务进程在文件执行后、结算前被强制终止，预留可能保持 `reserved` 且工作区丢失。现阶段采用**冻结预留、避免重复扣费或超额使用**的保守处理方式，运营者应人工核对后修复；公开收费前必须实现带证据的恢复、审计与退款机制。

## API

用户登录后，GET 接口使用用户会话 Cookie：

- `GET /api/billing/status`：查询当前 UTC 月份的免费余额，以及会员是否生效、到期时间。
- `GET /api/billing/catalog`：服务端定义的订阅套餐和 `checkout_enabled: false`。
- `GET /api/billing/orders`：仅返回自己的订单。

`POST /api/billing/orders` 接受 `{"sku":"member_monthly"}` 或 `{"sku":"member_yearly"}`（要求 Cookie、同源 Origin 和 CSRF），生成仅用于内部测试的 **pending** 订单，返回 `checkout_url: null`。没有客户端确认付款接口；账单信息不能被用户重写。最多允许五笔未完成订单，防止无限刷单。

`POST /api/workspaces/apply` 自动按最终更名数量计费：非会员超出免费额度时返回 HTTP **402**、`code: quota_exceeded`，不改动文件；会员直接放行且不计量。

## 手工核销接口（仅离线受信任管理员）

只有能访问服务端 SQLite 数据库的运营人员，在**独立验证外部支付渠道确实已到账、金额无误**之后，才可执行：

```bash
python -m rnbatch.web_billing --db /data/users.sqlite3 confirm-offline \
  --order <32位订单编号> --payment-reference <外部渠道真实唯一交易号>
```

此命令不会发起支付，也**没有**对应 HTTP 路由。支付凭据全局唯一、同一订单重复核销幂等，避免重复发放额度。不要将这些操作权限暴露给普通用户；严格保护数据库、后台 Shell 和备份。

## 正式支付上线的未完成事项

1. 注册合规商户并确定用户市场及适用的税务、退款、用户协议和隐私政策。
2. 接入真实支付服务商的**服务端**下单接口；生产使用 HTTPS + 安全密钥管理，并由服务端验证签名、时间戳、金额、商户订单号与交易状态。不能相信前端的支付成功提示。
3. 实现可靠的异步通知去重、支付结果主动查单、金额核对、对账、退款、争议处理和审计。
4. 升级为持久化任务与文件存储/删除审计，并增加上传恶意文件隔离、解析沙箱、速率限制和监控。
5. 完成 Chrome / Safari / Edge 浏览器 E2E、多人并发、断电恢复、支付安全及个人信息合规核验。
6. 拟定并实测价格、单用户成本、用户留存和真实付费转化率，再启用公开下单。
